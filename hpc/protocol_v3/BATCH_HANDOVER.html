V3 exclusive-node batch launcher

The batch launcher changes scheduling only. The frozen framework code, scientific sample cap, seeds, five-thread budget, per-task two-hour watchdog, original result files and CPU/RAM estimation method remain in use. One measured workload executes per physical node at any time. This is CPU computation on Artemis, with CodeCarbon estimates rather than hardware-metered energy.

What improves, and what does not

Each array element reserves one exclusive Artemis node for up to 12 hours and launches its assigned tasks sequentially. No new Slurm allocation is required between those tasks. Four elements can reserve four nodes if resources, priority and association limits permit. This reduces queue gaps; it does not accelerate algorithms, guarantee four nodes, or guarantee an earlier finish. Longer requests may wait longer for an allocation.

The launcher refuses to start another task unless the full two-hour watchdog plus ten minutes of headroom remains. A batch may therefore release its allocation early with tasks left over. Prepare a new plan for those remaining tasks after every batch has drained. Do not extend an individual scientific timeout.

Cancel pending old tasks only, then let running and completing tasks finish. Never cancel an active task to make this handover. Check current hardware availability separately. No pending task has scientific results to lose.

Prepare preserves eligible completed tasks and creates disjoint task lists for the remaining work. Failed or incomplete attempts require review and explicit --retry-task ID options at preparation; there are no automatic retries. Old attempts and hashes are retained. Check the counts and allocation before submission.

"$AWAREML_MAIN_PY" hpc/protocol_v3/batch_launcher.py submit --plan "$V3_BATCH_PLAN"

Submit exactly once. A submission marker blocks repeats, including uncertain submission outcomes. If submission errors, inspect the marker and Slurm before any retry. A second execution of a shard is also blocked. Do not manually remove these protections to rerun work; prepare a new reviewed plan after the old jobs drain.

Failure and measurement safeguards

Each task calls the unchanged scripts/awareml_v3.py run supervisor in a separate process. Its own energy interval, memory sampling, watchdog and attempt files remain independent of other tasks. CPU model, host memory capacity and Slurm thread budget are checked on every selected node. Existing AwareML and CodeCarbon locks cause a stop; the launcher never deletes locks automatically. Hardware models match the preserved EPYC 7763 baseline. This does not make estimated CPU or RAM power a direct meter reading.

A failed backend, missing energy or invalid result stops that shard before another task starts. Inspect the logs and attempt before deciding on an explicit retry. Successful completed results are never overwritten. Collection should retain all attempt history and explicitly select the reviewed successful retries, including task 39.

Monitoring changes

Slurm now counts node batches, not framework tasks. A completed array element may have completed many tasks, stopped at an allocation boundary, or have unrun tasks remaining. Read plan/shard_N.summary.json and campaign runs/task_*/attempt_*/result.json for scientific progress. Plan logs contain per-task completion records. Do not add Slurm batch completion counts to benchmark counts.

External data remain excluded from training and model selection. This launcher does not create or execute an external campaign automatically.
